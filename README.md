# 计划工程 · project-plan

让 AI 先把计划写出来、多方向盲审、在预算内把那些棘手的问题挖出来并解决掉
**你批准之后才许动手**。

> 还在为大肥鱼头脑简单而皮质醇爆上？还在为了数百轮的方案改动、审查、验收烧空余额？这样的场景，此时此刻正在 CN 各地上演，YOU COULD BE NEXT! 除非你选择 project-plan！

这是一个 **DSH**（DeepSeek Harness）的 skill：主会话当 planner，只负责派单；起草者 / 审查者 / 执行者 / 验收者都是子 agent，各写各的文件。问题带 `F-###` 编号跨轮追到关掉，预算按档位计数，用户说「批准 v{N}」才许执行。

## 和「让 AI 直接干」有什么不一样

|        | 直接让 AI 干      | 只让它写一稿计划       | project-plan                                          |
| ------ | ------------- | -------------- | ----------------------------------------------------- |
| 谁写     | 主会话边想边改文件     | 一个 agent 一口气写完 | 起草者子 agent，只写 `plan.md`，不碰代码                          |
| 谁审     | 没人            | 你自己读一遍         | 3~6 个审查者**互相看不见**，各写各的 `reviews/`                     |
| 问题去向   | 说过就忘，改完不知道漏没漏 | 你提一句它改一句       | `F-###` 编号跨轮追踪，每条必须有结局（fixed / deferred / unresolved） |
| 预算     | 无             | 无              | 短 / 普通 / 长三档，轮次、重开、回炉都有上限，脚本只认磁盘记录                    |
| 什么时候动手 | 立刻            | 你催了才动          | 重算指纹 + 你说「批准 v{N}」，缺一个都不许执行                           |
| 验收     | 看运气           | 无              | 另一个新实例逐条跑 `VC-###` 判据，产出 `verify/`                    |
| 留下什么   | 一堆 diff       | 一段聊天记录         | 一个 `runs/<slug>/` 目录，半年后还能复查                          |

## 什么时候该用

**用**：要做的东西超过一个文件、有几步、会改真实数据或不可逆；或者你已经在问「这计划行不行」。
**用 plan-only**：只要一份能评审的计划，不打算马上动手。
**不用**：一句话能说完的改动、纯问答、只要一段代码——直接做，这套流程的成本是几十次派单。没人能拍板的项目也别用：每一步都要求你说一句，审批永不自动完成（故意的）。

## 功能

- **五个角色、九个阶段**：planner（主会话，只派单）/ 起草者 / 审查者 / 执行者 / 验收者，外加一个隐藏的修复复核者。阶段 0 需求 → 1 起草 → 2 审查 → 3 合并处置 → 3.5 确认延后 → 4 批准 → 5 执行 → 6 验收 → 7 报告。
- **多方向盲审**：每轮按档位派 3~6 个审查者，方向互不重叠（可执行性 / 判据 / 依赖 / 风险 / 范围 / 反向），**互相看不见对方的结论**；主会话只做去重与合并，不改写结论。审查者只有「哪不成立」，没有「通过」权；批准权只在你手里。
- **F 编号闭环**：每条问题一个 `F-###`，从提出到关掉全程可追。第二轮起只给审查者 diff，逼它盯改动而不是重读全文。
- **预算看得见**：短 3 路 / 1 轮，普通 4 路 / 2 轮，长 5~6 路 / 3 轮；重开、回炉另有上限。`budget-check.mjs` 直接从磁盘数，不认主会话的自我汇报。
- **三条收敛纪律**：每轮只修 P1（严重漏洞）；平均每条修复超 15 行就拆批；起草者复用、审查者每轮新开。这是被两次跑爆的实测换来的（见「实测记录」）。
- **十道机器闸门**：编号连续、覆盖双向、每条 F 有结局、改动面、预算、派单回执、合批、验收、状态，各由一个脚本只查一件事，全部零依赖。
- **只审计划不执行（plan-only）**：`run/mode` 写 `plan-only`，只跑 0–4 和 7，交一份可评审的计划就收工；转执行要先校验指纹，对得上才许切。
- **需求澄清（可选）**：阶段 0 之前先问清。装了 [`grill`](https://github.com/nagi-studio/skills/tree/main/skills/pondering/grill) 就调它，没装走内置 5 问；三条触发命中一条才问，说「直接办」可跳。另外**强烈建议**装 grill skill以助于计划的阶段0工作，强烈建议！！！
- **修复复核与变更批**：批准后又要改，不能自己说了算——新实例只读 `plan.md` 与处置表复核「改在哪、波及什么」，然后回炉 + 重批 + 重算指纹。

## 审查环节怎么跑

一轮审查是四个动作，不是「让 AI 看看」：

1. **派单**：同一轮的 N 个审查者必须在**一条消息**里派完（分几条派出的按「未派满」处理），每人只拿到一份路径清单。
2. **各写各的**：每人只审一个方向，只写 `reviews/R{n}-{方向}.md` 一个文件，用本地号 `A-1 / B-1 / C-1`。
3. **合并**：主会话去重、分配全局 `F-###`，写 `R{n}-index.md`；`check-index.mjs` 对账「表头数字 vs 实际行数」。
4. **处置 + 复核**：起草者逐条写 `fixed / deferred / unresolved`（`R{n}-answer.md`），再由**一个新实例**只读 `plan.md` + `answer` + `index` 复核「改在哪、波及什么」，产出 `R{n}-fixcheck.md`。它不看原始 findings——所以查不出「漏改」，只能查出「假改」。

### 四个方向

| 方向 | 审什么 |
| --- | --- |
| A 设计 | `## 备选方案`：舍弃理由成立吗？有没有更简单的路？这事有必要做吗？ |
| B 计划 | `## 任务` / `## 验收` / `## 风险`：依赖顺序、判据能不能证明结论、失败路径与回滚 |
| C 无方向 | 自己扫，专捞 A、B 都没覆盖的；不重复 A、B 已报的 |
| X 现写 | 主会话给一句「这项目最可能死在哪」，按那句审；普通档 1 个、长档 2 个 |

### 一条 finding 长什么样

四行封顶。指不出 `plan.md` 行号的不算 finding，算印象：

| 严重度 | P1 |
| --- | --- |
| 证据 | `plan.md:25-87` 排了 5 个 Task；`run/user-words.md` 里「这是小修改、别重开好几轮」没有落盘 |
| 影响 | 审查与执行都按 5 个 Task 走，短档只给 1 轮，任一步失败就撞上用户预先说的「别重开」 |
| 建议 | 原话补进 `user-words.md`，`plan.md` 加一行改动面对照；对不上就把 Task-3/4 移出本轮 |

### 盲到什么程度

- 不给 `reviews/`（包括往轮、包括同轮别人的）、不给上一轮摘要、不给对话历史。
- 第 2 轮起只给 diff，并明说「先读 diff，只对改动及其波及下手」——防它把上一轮的话再说一遍。
- 审查者**没有通过权**：只说「哪里不成立」，不说「通过」；全局编号也不许它编，编了必撞。
- 起草者不能给自己出审查结论；同轮审查者互相串供，该轮作废。

## 跑起来长什么样

一个 run 就是磁盘上一个目录，状态全在里面，换会话也能接着跑（`node scripts/status.mjs <runDir>` 一屏恢复）：

```text
status · plan-skill-v6-grill
① 档位与部件  档位: 短 | 部件 待定（起草后补） | planner | 2026-11-10T13:51
② 阶段  DONE（显式：run/report.md 已生成，验收全 pass）
   轮次  当前 R1 · 已用 R1 · 作废 无
③ 预算  审查轮 1 / 1（剩 0） · 重开 0 / 2（剩 2） · 回炉 0 / 1（剩 1）
④ reviews  R1: A, B, C, answer, fixcheck, index
⑤ verify  V1.md（pass 9 / fail 0 / unresolved 0） · 合计 pass 9 / fail 0 / unresolved 0
⑥ STATE  停在哪：DONE（阶段 7 完成，check-final exit 0） / 为什么：9 条 VC 全过，报告与闸门收口。 / 下一步：交付完成，可归档
⑦ 下一步  DONE：交付完成，可归档
⑧ 批准  已批准（v2，sha256 一致）
模式: full
```

目录结构：

```text
runs/<slug>/
├─ run/         user-words.md（用户的逐字原话）、dispatch.log、fingerprint.txt、
│               decisions.md、F-log.md、report.md、mode、STATE.md
├─ REQ.md       需求：每条逐字引用原文 + 判据 + 确认方式、确认原话
├─ plan.md      计划：备选方案 / Task-# / VC-### / 风险
├─ reviews/     R{n}-{方向}.md（盲审）、R{n}-index.md（合并）、R{n}-answer.md（处置）、R{n}-fixcheck.md（复核）
├─ evidence/    执行证据：命令原文 + 完整输出 + 时间戳
└─ verify/      V{n}.md：逐条 VC 判定
```

## 环境要求

| 需要                        | 说明                                                           |
| ------------------------- | ------------------------------------------------------------ |
| DSH（DeepSeek Harness）     | 流程靠 DSH 的子 agent 派单；没有 DSH 用不了（它不是通用的提示词模板，是宿主里的 skill）      |
| Node ≥ 18                 | 全部脚本只用 Node 内置模块，**没有 npm 依赖**，不用 `npm install`              |
| Git Bash / WSL（仅 Windows） | 计划和模板里的证据命令用 `sha256sum`、`sed`、`awk`、`find`；Linux / macOS 自带 |

## 安装

skill 的加载规则是「`$DSH_HOME/skills/<name>/SKILL.md` 存在即生效，且只在新会话加载」。所以装法就是把它放到那个位置。

### 渠道一：直接 clone 到 skill 目录（推荐）

```bash
git clone https://github.com/Night-Leaf/project-plan "$DSH_HOME/skills/project-plan"
```

`DSH_HOME` 通常是 `D:/DSH/home`（Windows）或 `~/.dsh`（macOS / Linux）。没设这个环境变量时，照样能跑脚本，只是 `pack-skill.mjs` 会提示你补上。

### 渠道二：手动复制目录

没有 git 也行：把仓库整目录复制成 `$DSH_HOME/skills/project-plan`，保证根目录有 `SKILL.md`、`plan-v3.md`、`prompts/`、`templates/`、`scripts/`。

### 渠道三：npm

没有。这是宿主内 skill，不是 npm 包，也没有发布到 registry；也不需要 release 附件，仓库根目录就是可用的全部内容。

### 装好之后

开一个**新会话**（旧会话不会重新加载 skill），说下面任意一句就会触发：

> 帮我写个计划 · 这份计划靠谱吗 · 审一下这个方案 · 先别写代码，先出计划 · 多找几个人挑毛病 · 计划做好了吗

或者在做多步、不可逆的改动前说「先把方案定死」。

### 只在仓库里开发，不想把它当 skill 装

仓库放在任意位置，改完规则或模板后同步过去：

```bash
node scripts/pack-skill.mjs            # 默认复制到 %DSH_HOME%\skills\project-plan
node scripts/pack-skill.mjs D:/other   # 或者指定目标目录
```

`pack-skill.mjs` 复制的是 `SKILL.md` + `plan-v3.md` + `prompts/` + `templates/` + `scripts/`。**skill 目录是产物，别直接改那里**，下次同步会被覆盖。

## 升级与卸载

**升级**：走渠道一的，`git -C "$DSH_HOME/skills/project-plan" pull`；走渠道二或开发目录的，重新 `pack-skill.mjs` 一次。装完要**开新会话**，旧会话仍在用旧规则。

**回滚**：skill 目录里是 git 仓库的话，`git checkout v1.0.0` 即可；否则升级前把整个目录复制一份，要回滚时复制回去。

**卸载**：删掉 `$DSH_HOME/skills/project-plan` 整个目录，开新会话。已经跑过的 `runs/` 不受影响，脚本可以直接指着老 run 目录跑。

## 可调项

流程没有配置文件，能调的都在 `run/` 里，或者由你在对话里一句定：

| 名称    | 取值                             | 默认     | 说明                                                  |
| ----- | ------------------------------ | ------ | --------------------------------------------------- |
| 模式    | `full` \| `plan-only`          | `full` | 写 `run/mode`；`plan-only` 跳过执行与验收，只交计划               |
| 审查档位  | `短` \| `普通` \| `长`             | 按计划规模定 | 短 3 路 1 轮 / 普通 4 路 2 轮 / 长 5~6 路 3 轮；越早定越省          |
| 审查方向  | 2~6 个                          | 3      | 每轮派几个审查者，方向互不重叠；方向由主会话按计划内容挑                        |
| 验收归属  | `自验` \| `独立`                   | `独立`   | `独立` = 另起一个新实例做验收；短档的小改动可以自验，报告里要写明                 |
| 需求澄清  | `grill` \| `fallback` \| `不需要` | 自动判断   | 三条触发（说不清验收标准 / 两条需求互斥 / 范围含糊）命中才问；写进 `dispatch.log` |
| 改动面阈值 | 行数                             | 15 行/条 | 平均每条修复超过它就停，拆两批；`check-diff.mjs` 量                  |
| 每轮修什么 | P1 优先                          | 只修 P1  | P2/P3 只能写 `deferred` 或 `unresolved`，不在这轮动手          |

## 使用

主会话自己不动手，只派单。你能下的指令其实只有几条：

| 你说               | 发生什么                                                  |
| ---------------- | ----------------------------------------------------- |
| 帮我写个计划 / 审一下这个方案 | 开一轮：先问需求，再起草、盲审、合并处置                                  |
| （回答 REQ 的确认问题）   | 阶段 0 只问一次，逐字进 `REQ.md`                                |
| 批准 v{N}          | 阶段 4 放行；主会话重算 `plan.md` 的 sha256 写进 `fingerprint.txt` |
| 只审不执行 / 先别动手     | 切 `plan-only`，跑完 0–4 和 7 就停                           |
| 这条可以延后 / 这些必须改   | 阶段 3.5：确认哪些 `deferred` 真的能延后                          |
| 再批一次 v{N+1}      | 回炉后重批；旧指纹作废，不许拿旧批准继续执行                                |

九个阶段：

| 阶段               | 谁做                 | 产出                                                  |
| ---------------- | ------------------ | --------------------------------------------------- |
| 0 需求             | 起草者                | `REQ.md`（用户只回一次话）                                   |
| 1 起草             | 起草者                | `plan.md`                                           |
| 2 审查             | 3~6 个审查者，**互相看不见** | `reviews/R{n}-{方向}.md`                              |
| 3 合并处置           | 主会话 + 起草者 + 新实例复核  | `R{n}-index.md`、`R{n}-answer.md`、`R{n}-fixcheck.md` |
| 3.5 确认延后         | 用户                 | 哪些 `deferred` 真的可以延后                                |
| 4 批准             | 用户                 | `fingerprint.txt`（plan 的 sha256）、`decisions.md`     |
| 5~7 执行 / 验收 / 报告 | 执行者、验收者（新实例）、主会话   | `evidence/`、`verify/`、`run/report.md`               |

## 机器闸门

流程最容易烂尾的地方都给了脚本，每个只查一件事。全部零依赖，`node scripts/xxx.mjs` 直接跑：

| 命令                                                          | 查什么                                                                 |
| ----------------------------------------------------------- | ------------------------------------------------------------------- |
| `node scripts/check-plan.mjs plan.md REQ.md`                | 编号连续、覆盖双向、必备字段、命令登记、路径冲突、判据里的模糊词                                    |
| `node scripts/check-index.mjs R{n}-index.md R{n}-answer.md` | 表头数字与行数对不对、每个 F 有没有结局、fixed 三栏填了没                                   |
| `node scripts/check-diff.mjs <runDir> plan.md <answer>`     | 改动面多大、每条 F 摊几行、有没有写「波及」                                             |
| `node scripts/budget-check.mjs <runDir> [短\|普通\|长]`         | 审查轮 / 重开 / 回炉用了多少——**只认磁盘，不认谁记的**                                   |
| `node scripts/check-dispatch.mjs <runDir> [短\|普通\|长]`       | 每轮回执：人数对档位、`one-message`、强度值域、`VOID` 原因                             |
| `node scripts/check-batch.mjs plan.md`                      | 两个 Task 的涉及文件有交集 → 应合批（exit 1）                                      |
| `node scripts/check-final.mjs <runDir>`                     | 验收闸门：verify、report 的验收归属 + 三数字 + V、档位/不可逆、指纹；plan-only 分支不要求 verify |
| `node scripts/status.mjs <runDir>`                          | 一屏八类状态 + 模式：档位 / 阶段 / 预算 / reviews / verify / STATE / 下一步 / 批准      |
| `node scripts/flow-check.mjs`                               | 流程模型有没有死路、不可达、无预算的环                                                 |
| `node scripts/guard-check.mjs`                              | 拓扑之外的条件守卫：「条件永远为真的迁移」这类看着能走、其实走不到的坑                                 |

## 常见问题

### 为什么不干脆让 AI 直接写代码？

因为它的错通常不在语法，在**你没说清楚、它没问、你也没检查**的地方。计划阶段逼的是这三件事：需求写成可验收的判据、任务拆到能单独执行、每条判据有命令能验证。写代码快，改方向慢。

### 批了之后我又想改怎么办？

不许主会话自己说了算。走「变更批」：3~5 条合成一个 Task（内部 `变更-1/2/3` 分节），仍要回炉、重批、重算指纹；含不可逆步骤的变更不许合批，只能单条走。

### 审查者互相看不见，会不会重复审同一件事、或者一起漏掉？

会重复，所以阶段 3 有一步去重合并，`check-index.mjs` 对账；会漏，所以有方向和轮次，而不是一个审查者审到底。**多方向不等于穷尽**，这一点写在「不保证什么」里。同轮审查者要是互相串供，该轮直接作废，不采信。

### 预算用完了问题还没收干净？

那就是 `unresolved`。它不会假装处理完：报告里要列出来，你决定是加一轮（重开或回炉都会扣预算）还是接受风险继续。预算的上限是拿来撞的，不是拿来篡改的。

### 能让它只出计划、不碰我的代码吗？

能。`run/mode` 写 `plan-only`，只跑阶段 0–4 和 7。之后想执行，先用 `fingerprint.txt` 校验 `plan.md` 没被改过，一致才许切 `full`，切换不重写指纹。

### 跑一次要多久、多少 token？

20~60 分钟，几十次派单。这是它的成本，也是它存在的理由——所以「一句话能说完的改动」别用它。快问快答、只要一段代码，直接让主会话做。

### 换了会话 / 换了模型，能接着跑吗？

能。状态全在 `runs/<slug>/` 里，`node scripts/status.mjs <runDir>` 一屏告诉你停在哪、下一步该谁动。这也是它不依赖「上一轮聊天记录」的原因。

## 不保证什么

- **不保证发现所有问题**——审查是抽样的，多方向也不等于穷尽
- **不保证计划能执行成功**——它只管计划本身，执行是另一件事
- **防不住「改完再改回来」**——指纹只看前后不一致，不看你改了什么
- **判据来源是起草者自评**——把「推断」标成「直述」就能少几行给你看，脚本判不出中文是不是推断
- **实现细节要另审**——计划阶段只该审「任务划分、依赖、判据能不能执行」；命令在某台机器上的具体行为，留给执行和验收

## 结构

```text
SKILL.md            skill 入口（205 行，日常照它走）
plan-v3.md          完整规则（390 行）
flow.model.json     流程模型：状态、迁移、每阶段的步骤与出口
prompts/            7 份 prompt：00 主会话 / 05 需求澄清 / 10 起草者 / 20 审查者 / 30 执行者 / 40 验收者 / 50 修复复核者
templates/          12 份文件模板：REQ / plan / R-方向 / R-index / R-answer / F-log / decisions / dispatch.log / evidence / verify / report / fingerprint
scripts/            22 个文件：生成器（gen-flow / gen-card）、检查器（check-* / budget / flow / guard / status）、
                    工具（mode / pack-skill / asar-extract / check-untouched）、回归测试（test-*.mjs + test/fixtures）
.github/workflows/  CI：Node 20 上跑全部闸门与回归
```

规则只有一个源头：`flow.model.json`。改它就改一切，然后：

```bash
node scripts/gen-flow.mjs plan-v3.md     # 重新生成 plan-v3.md 的流程段
node scripts/flow-check.mjs              # 确认没死路
node scripts/guard-check.mjs             # 确认没有「条件永远为真」的迁移
node scripts/pack-skill.mjs              # 同步到 skill 目录
```

`plan-v3.md` 里的 FLOW 段是生成的，**别手改**；手改会在下次生成时丢。
