# 需求澄清

开工前问清楚，再进阶段 0。问完没有新信息就停，别把澄清做成第二份需求文档。

## 什么时候用

命中任一条就做；三条都不沾，直接进阶段 0。

- **说不清验收标准**：用户说"能用就行""看着办"，没人能判断做成什么样算完。
- **两条需求互斥**：既要离线可用，又要实时同步；两边都写进 REQ 就会在阶段 3 打架。
- **范围含糊**：一句话里塞了三件事，或者"顺便把 X 也改了"，边界没人划过。

## 怎么问

- 一次一条或几条，看用户能回答的节奏；用户一次答完就往下走，别按题号硬走流程。
- 不堆低价值问题：能自己读代码、读配置查到的，不问；问了也不改变下一步的，不问。
- 用用户的原词问，别先翻译成方案名；用户答不上来时给两三个候选，别留开放式大坑。
- 先问 Q1、Q3、Q5，这三条最可能改方向；Q2、Q4 能自己查就先自己查。

## 五个问题

### 问题 1：真正要解决什么

说明：分清症状和目标，定下怎么算做完，并划出这次明确不做的事。

例子：用户说"导出老是失败"——症状是按钮报错，目标可能是"能导出成 Excel"；验收是导出的文件能打开且数据对得上；这次不做批量导出。

### 问题 2：哪些已经定了

说明：列出不能碰的约束，包括技术栈、既有接口、上线时间和别人的依赖。

例子：用户说"只能跑在内网，数据库不能换"——这两条写进约束，后面选方案时不再讨论。

### 问题 3：哪些还没定

说明：把需要用户拍板的选择单独列出来，别替他默认。

例子：登录用账号密码还是企业微信扫码，用户没说；这是 Q3，不是执行者自己能决定的。

### 问题 4：哪些前提是默认成立、但没验证

说明：把"大家都这么以为"的假设挑出来，标明没验证，别让它悄悄变成计划的地基。

例子：默认测试环境有外网，实际是隔离的——这条不验证，后面所有联调步骤都会塌。

### 问题 5：哪个取舍会改变后续方向

说明：找出那个选了 A 就不能回头做 B 的决定，让用户先选，别等做到一半才发现。

例子：先做单机版还是先做多人协作——选了单机版，数据模型后面很难改成协作。

## 什么时候跳过

- 出口：用户说"直接办 / 不用问 / 就按我说的"→ 记 `需求澄清: 不需要 | 用户要求直接办`，跳过澄清，直接进阶段 0。
- 停止条件：最多问 1–2 轮；剩余未知不挡下一步就停，把未知记进 `run/decisions.md` 的待定项。

## 答完写回哪

- 用户回答逐字追加到 `run/user-words.md` 的 `## 需求澄清（问答）`，不重写文件开头的原话。
- 结论、取舍、待定项进 `run/decisions.md`；问不出结论也要写一行，别让下一轮从零猜。

## 例子

用户："插件面板一直连不上 GitHub，你看着修。"
澄清：连不上时界面是什么样？是列表空白，还是安装时报错？
澄清：你要的是"面板能列出仓库并装上一个插件"，还是"能显示 GitHub 热门榜单"？这次明确不做什么？
结论：症状是列表空白；目标是能装插件；验收=面板能列出仓库并装成一个；这次不做榜单和搜索。
